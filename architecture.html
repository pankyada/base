Architecture ​

Harness is a profile-driven agent runtime. One process exposes WebSocket and HTTP entry points, then runs the profile selected for each request. A profile owns its model, prompt, tools, safety policy, memory, automations, and optional voice configuration; the runtime stays generic.

The interactive architecture explorer (source: docs/architecture-site/ in the repo) is the canonical, detailed architecture doc — every layer, module, file, and the design choices that differ from a typical agent harness (conditional ACL, the provenance gate, durable deferred asks, watch/poll triggers, autonomy budgets, temporal memory, channels). This page is the shorter operator-facing summary: request lifecycle, runtime boundaries, and how to actually run and extend the thing.

For a narrative view of the same runtime — what a specific use case actually does, beat by beat, rather than the full component map — see How it Works. The explorer is the map; the films are the story. (See ADR-73.)

Request lifecycle ​

  1. The server loads one profile or a directory of profiles. A directory is registered by profile name; an invalid YAML file is logged and skipped.
  2. A WebSocket hello.profile, REST request profile, trigger owner, or channel binding selects the profile. Unknown names fail explicitly.
  3. Harness creates or resumes a session. Session history is append-only; user memory is shared while profile and project memory stay scoped.
  4. The loop projects the ledger into a bounded provider request, streams model output, executes approved tool calls, and repeats until final output.
  5. Effectful calls pass ACL predicates, budgets, provenance gates, hooks, and audit logging. Tool output is fed back into the ledger with its provenance.
  6. The session, usage, telemetry, artifacts, pending inputs, and audit records persist under ~/.harness or the profile artifact directory.

Runtime boundaries ​

Shared process servicesPer-profile state
HTTP/WS server, telemetry writer, audit journal, model-client pool, user memorysessions, profile/project memory, prompt, tool view, ACLs, budgets, trigger owner, MCP client set, channel runtime

One process is a convenience boundary, not crash isolation. Run separate server processes when a profile needs a separate failure domain.

Optional semantic decisions ​

An optional profile-owned decision service evaluates bounded task and candidate state through a separate Jev adapter. It can advise capability exposure, memory capture/recall/retention, workflow routing, compaction and result/failure handling. It is off by default; each feature supports disabled, shadow and enforce modes. Shadow is the recommended starting point while thresholds remain uncalibrated.

This service changes context selection, not execution authority. The loop keeps its full permitted execution registry for normal gates and pending-call resume. Explicit skills, required controls, discovery recovery and explicit pins retain priority. Memory candidates still pass structural scope/time filters; no vector store or transcript retrieval is added. Retention is reversible, and semantic advice never authorizes deletion or upgrades source trust.

Remote use requires explicit outbound-state consent and a credential environment variable. Calls remain bounded by request, time and cost limits; telemetry avoids raw content. See the operator guide for YAML, recovery behavior and offline/live evaluation. Current implementation and calibration acceptance are tracked separately in PT-068 and PT-069.

Use it ​

1. Install and run the bundled profile family ​

bash
curl -fsSL https://raw.githubusercontent.com/pankyada/base/main/scripts/install.sh | sh
export OPENAI_API_KEY='...'
harness-server --profiles ~/.harness/profiles --default-profile coding

The installer keeps an existing ~/.harness/profiles/ directory. Each bundled YAML carries its adjacent Markdown prompt, so no repository-relative prompt path is required.

2. Call a selected profile through REST ​

bash
curl http://localhost:7337/run \
  -H 'content-type: application/json' \
  -d '{
    "profile": "coding",
    "user": "pankaj",
    "input": "Explain src/context/projection.ts"
  }'

Use POST /stream for server-sent token/tool events. GET /health reports the default profile and every loaded profile.

3. Select and switch profiles over WebSocket ​

json
{ "type": "hello", "user_id": "pankaj", "profile": "coding" }

Later on the same connection:

json
{ "type": "set_profile", "profile": "research" }

Each switch starts a fresh session with the selected profile's prompt, model, memory scope, tools, and channel runtime.

4. Define a small guarded agent ​

yaml
name: release-notes
model:
  base_url: https://api.openai.com/v1
  api_key_env: OPENAI_API_KEY
  id: gpt-5.4-mini-2026-03-17
system_prompt: ./release-notes.md
working_dir: $CWD
artifact_dir: .harness/release-notes
mode: production
tools:
  builtin:
    Read: allow
    Grep: allow
    Write: prompt
  mcp_servers: []
triggers:
  budget:
    max_cost_usd: 0.25
    max_tools: 20
    max_wall_s: 120

release-notes.md lives beside the YAML. $CWD is deliberate runtime input: start Harness in the repository you want the agent to inspect.

The browser client is built separately with pnpm --filter harness-web build. Set NEXT_PUBLIC_HARNESS_WS_URL and NEXT_PUBLIC_HARNESS_HTTP_URL to a reachable server, and add the browser origin to HARNESS_ALLOWED_ORIGINS.

5. Add streaming voice without adding a vendor to core ​

Put a provider module under .agents/voice/, then reference its provider name:

yaml
system_prompt: ./assistant.md
system_prompt_voice: ./assistant-voice.md
voice:
  stt: { provider: local-stt, config: {} }
  tts: { provider: local-tts, config: { voice: calm } }
  endpointing: { silence_ms: 700, max_utterance_s: 60 }
  barge_in: true

An audio-capable client sends hello.audio_supported: true, audio_start, binary frames, and audio_end. Harness emits partial transcripts and binary audio output. Barge-in aborts synthesis and the model turn, then preserves an interrupted partial in the session ledger.
