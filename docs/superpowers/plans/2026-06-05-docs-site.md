# Getting Started

## Prerequisites

- [Node.js](https://nodejs.org) 20+ and [pnpm](https://pnpm.io) 9+
- An API key for your model provider (Anthropic or OpenAI-compatible)

## Installation

```bash
git clone https://github.com/pankyada/base.git
cd base
pnpm install
```

## Configuration

```bash
cp .env.example .env
```

Edit `.env` and set your API key:

```
ANTHROPIC_API_KEY=sk-ant-...
# or OPENAI_API_KEY=sk-...
```

## Start the TUI (recommended)

```bash
pnpm tui
```

`pnpm tui` auto-starts the server in the background, waits until it's healthy, then launches the terminal UI. Quit with `Ctrl+C` — the server shuts down with it.

Use a specific profile:

```bash
HARNESS_PROFILE=devops pnpm tui
```

## Start the server only

```bash
pnpm dev                          # default profile (~/.harness/profiles/coding.yaml)
pnpm dev profiles/devops.yaml     # path to a profile YAML
```

Server listens on port `7337`. Override with `HARNESS_PORT`.

## Connect the web client

With the server running:

```bash
cd web && pnpm dev
```

Open [http://localhost:3000](http://localhost:3000).

## One-shot REST call

```bash
curl -X POST http://localhost:7337/run \
  -H 'Content-Type: application/json' \
  -d '{"input": "What is 2 + 2?"}'
```

Response:

```json
{
  "output": "4",
  "usage": { "input_tokens": 12, "output_tokens": 1 },
  "session_id": "abc123"
}
```

## Docker Compose (full stack)

```bash
docker compose up
```

Web client: [http://localhost:3000](http://localhost:3000)
Backend: [http://localhost:7337](http://localhost:7337)

Session data, memory, and telemetry are persisted to `.harness-data/` on the host.

## What's next?

- [Profiles](./profiles) — configure models, tools, and triggers
- [Built-in Tools](./builtin-tools) — what the agent can do
- [MCP Servers](./mcp-servers) — connect external tools
```

- [ ] **Step 1: Write profiles.md**

````markdown
# Profiles

A profile is a YAML file that defines one agent instance: its model, system prompt, tools, memory, hooks, and triggers.

Profiles live in `profiles/` (project-local) or `~/.harness/profiles/` (user-global).

## Minimal profile

```yaml
name: my-agent
model:
  base_url: https://api.anthropic.com/v1
  api_key_env: ANTHROPIC_API_KEY
  id: claude-sonnet-4-6
system_prompt: prompts/my-agent.md
artifact_dir: .harness/my-agent
```

## Field reference

### `name` _(required)_

Human-readable identifier. Shown in logs and the TUI status bar.

---

### `model` _(required)_

| Field | Type | Description |
|-------|------|-------------|
| `base_url` | URL | OpenAI-compatible endpoint. Use `https://api.anthropic.com/v1` for Anthropic. |
| `api_key_env` | string | Name of the env var holding the API key (e.g. `ANTHROPIC_API_KEY`). |
| `id` | string | Model ID passed to the API (e.g. `claude-sonnet-4-6`, `gpt-4o`). |
| `fallback_id` | string? | Model to fall back to on rate-limit or model unavailability. |

---

### `system_prompt` _(required)_

Path to a Markdown file used as the system prompt. `$CWD` expands to `process.cwd()`, `~` to the home directory.

```yaml
system_prompt: prompts/devops.md
```

---

### `artifact_dir` _(required)_

Directory where the agent stores files it creates (memory, reports, drafts, etc.).

```yaml
artifact_dir: .harness/devops
```

---

### `working_dir` _(default: `$CWD`)_

Directory the agent considers its working root for relative paths.

---

### `mode` _(optional)_

Sets the trust model and default tool ACLs. Individual `tools.builtin` overrides still apply, but **mode wins on conflict**.

| Mode | Use case | Bash | Write/Edit | ExecuteCode |
|------|----------|------|-----------|-------------|
| `developer` | Local dev, single-tenant | allow | allow | allow |
| `analyst` | Data analysis, sandboxed | deny | deny | allow |
| `assistant` | Chat assistant, multi-tenant | deny | deny | deny |
| `production` | Customer-facing, strict | deny | deny | deny |

```yaml
mode: analyst
```

> **No mode = explicit ACLs.** The example profiles in `profiles/` intentionally omit `mode:` and use explicit ACLs for full control. See the annotated example below.

---

### `tools`

```yaml
tools:
  builtin:
    Bash: allow      # allow | prompt | deny
    Write: deny
  custom:
    "*": prompt      # wildcard fallback for custom tools
  mcp_servers:
    - name: github
      transport: stdio
      command: npx
      args: ["-y", "@modelcontextprotocol/server-github"]
      env:
        GITHUB_TOKEN: "${GITHUB_TOKEN}"
      acl:
        list_pull_requests: allow
        "*": prompt
```

|------|---------|

| Write | allow |
| Edit | allow |
| Bash | prompt |
| Grep | allow |
| Glob | allow |
| Skill | allow |
| MemoryRead | allow |
| MemoryWrite | allow |
| MemoryList | allow |
| MemoryDelete | allow |
| Stats | allow |
| Delegate | prompt |
| ExecuteCode | allow |

### `hooks`

Shell commands that run at tool lifecycle points. See [Hooks](./hooks) for details.

```yaml
hooks:
  pre_tool: []
  post_tool: []
  on_stop:
    - "git add .harness/writer/drafts 2>/dev/null || true"
  timeout_ms: 5000
```

---

### `improvement`

Post-session reflection and skill mining.

```yaml
improvement:
  enabled: true
  model_id: claude-haiku-4-5-20251001   # optional, defaults to profile model
  mine_skills_every_n_sessions: 10
```

---

### `context_window`

```yaml
context_window:
  max_tokens: 100000
  model_id: claude-haiku-4-5-20251001   # optional cheaper model for summarisation
```

---

### `memory`

```yaml
memory:
  provider: fs      # fs (default) | graph
```

See [Memory](./memory) for details.

---

### `max_depth`

Maximum sub-agent delegation depth. Default `2`. Prevents infinite recursive delegation.

```yaml
max_depth: 3
```

---

### `agents`

Declare sub-agent workers with typed I/O. See [Multi-Agent](./multi-agent) for details.

```yaml
agents:
  - name: researcher
    profile: ./researcher.yaml
    input:
      query: { type: string }
    output:
      findings: { type: array }
```

---

### `contract`

Typed I/O contract validated by [AJV](https://ajv.js.org) on every call to `POST /run`. Returns HTTP 422 on violation.

```yaml
contract:
  input:
    type: object
    required: [topic, format]
    properties:
      topic: { type: string }
      format: { enum: [blog, changelog, email, docs] }
  output:
    type: object
    properties:
      draft: { type: string }
```

---

### `triggers`

```yaml
triggers:
  cron: "0 8 * * *"           # daily at 08:00 (node-cron syntax)
  cron_input:
    task: "Run daily health check"
  webhook: false               # set true to enable POST /webhooks/<profile-name>
```

> **Constraint:** `mode: developer` combined with any trigger throws a hard validation error at startup. Use explicit ACLs instead.

---

### `interop`

```yaml
interop:
  a2a: false    # expose GET /.well-known/agent.json + POST /a2a
  acp: false    # expose ACP REST endpoints
```

---

### `executor`

Required to use the `ExecuteCode` tool. See [Built-in Tools](./builtin-tools#executecode).

```yaml
executor:
  default: docker          # wasm (browser Pyodide) | docker
  fallback: docker
  docker_image: python:3.12-slim
  timeout_ms: 30000
  allowed_packages:
    - pandas
    - numpy
```

# Built-in Tools

The harness ships 18 built-in tools. ACL for each is set in `tools.builtin` of the profile YAML (or inherited from `mode:`).

## ACL values

| Value | Meaning |
|-------|---------|
| `allow` | Tool executes without prompting |
| `prompt` | User must approve each call at runtime |
| `deny` | Tool call rejected immediately |

---

## File tools

### `Read`

Read a file. Returns content with line numbers (`cat -n` format).

**ACL default:** `allow`

| Param | Type | Required | Description |
|-------|------|----------|-------------|
| `file_path` | string | yes | Absolute path to file |
| `offset` | number | no | Start line, 1-indexed (default 1) |
| `limit` | number | no | Max lines to read (default 2000) |

```json
{ "file_path": "/etc/hosts", "offset": 1, "limit": 50 }
```

---

### `Write`

Write content to a file, creating parent directories as needed.

**ACL default:** `allow`

| Param | Type | Required | Description |
|-------|------|----------|-------------|
| `file_path` | string | yes | Absolute path to file |
| `content` | string | yes | Content to write |

---

### `Edit`

Replace an exact string in a file.

**ACL default:** `allow`

| Param | Type | Required | Description |
|-------|------|----------|-------------|
| `file_path` | string | yes | Absolute path to file |
| `old_string` | string | yes | Exact text to find (must be unique unless `replace_all`) |
| `new_string` | string | yes | Replacement text |
| `replace_all` | boolean | no | Replace every occurrence (default false) |

---

### `Grep`

Search for a regex pattern in files.

**ACL default:** `allow`

| Param | Type | Required | Description |
|-------|------|----------|-------------|
| `pattern` | string | yes | Search pattern |
| `path` | string | yes | File or directory to search |
| `flags` | string | no | grep flags (default: `-rn`) |

---

### `Glob`

Find files matching a glob pattern.

**ACL default:** `allow`

| Param | Type | Required | Description |
|-------|------|----------|-------------|
| `pattern` | string | yes | Glob pattern (e.g. `src/**/*.ts`) |
| `cwd` | string | no | Working directory (default: `process.cwd()`) |

---

## Shell tool

### `Bash`

Execute a bash command. stdout + stderr combined.

**ACL default:** `prompt`

| Param | Type | Required | Description |
|-------|------|----------|-------------|
| `command` | string | yes | Shell command |
| `timeout` | number | no | Timeout in ms (max 120000, default 120000) |

---

## Skill tool

### `Skill`

Load and return a skill by name. Returns the full `SKILL.md` content.

**ACL default:** `allow`

| Param | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | yes | Skill name as listed in the skill index |

---

## Memory tools

All memory tools operate on one of three scopes:

| Scope | Storage | Lifetime |
|-------|---------|---------|
| `session` | In-memory on `Session` | Until session ends |
| `profile` | `<artifact_dir>/memory/*.md` | Persistent, shared across all users |
| `user` | `~/.harness/memory/<profile>/<user>/*.md` | Persistent, private to one user |

### `MemoryRead`

**ACL default:** `allow`

| Param | Type | Required |
|-------|------|----------|
| `scope` | `session` \| `profile` \| `user` | yes |
| `key` | string | yes |

### `MemoryWrite`

Default scope is `user` (private). Use `profile` to share across all users.

**ACL default:** `allow`

| Param | Type | Required | Description |
|-------|------|----------|-------------|
| `scope` | `session` \| `profile` \| `user` | no | Default: `user` |
| `key` | string | yes | Short slug (e.g. `project-context`) |
| `content` | string | yes | Markdown content |
| `links` | array | no | Graph links: `[{ target: "other-key", relation: "depends_on" }]` |

### `MemoryList`

**ACL default:** `allow`

| Param | Type | Required |
|-------|------|----------|
| `scope` | `session` \| `profile` \| `user` | yes |

### `MemoryDelete`

**ACL default:** `allow`

| Param | Type | Required |
|-------|------|----------|
| `scope` | `session` \| `profile` \| `user` | yes |
| `key` | string | yes |

### `MemoryLinked`

Graph traversal — finds entries that the key links to (forward) and entries that link to the key (reverse).

**ACL default:** `allow`

| Param | Type | Required | Description |
|-------|------|----------|-------------|
| `scope` | `session` \| `profile` \| `user` | yes | |
| `key` | string | yes | Anchor memory key |
| `relation` | string | no | Filter by relation type |

## User interaction tools

### `AskUser`

Pause the agent loop and ask the user a question. Resumes when the user responds.

**ACL default:** `allow`

| Param | Type | Required | Description |
|-------|------|----------|-------------|
| `prompt` | string | yes | Question to ask |
| `kind` | `text` \| `select` \| `multi_select` | yes | Input type |
| `options` | string[] | no | Required for `select` and `multi_select` |

### `TodoWrite`

Replace the current session todo list. Always pass the complete list — this overwrites everything.

**ACL default:** `allow`

| Param | Type | Required |
|-------|------|----------|
| `items` | `{ id, content, status, priority }[]` | yes |

# MCP Servers

MCP (Model Context Protocol) servers extend the agent with external tools. Configure them in `tools.mcp_servers` of the profile YAML.

## Tool naming

MCP tools are exposed to the agent as `<serverName>__<toolName>`. For example, a server named `github` with a tool `list_pull_requests` becomes `github__list_pull_requests`. Tool parameter schemas are passed through from the server's `listTools` response.

## Transport types

`transport` defaults to `stdio` if omitted.

### `stdio` — local subprocess

Launches a local process and communicates over stdin/stdout. Most MCP servers use this transport.

```yaml
tools:
  mcp_servers:
    - name: filesystem
      transport: stdio       # optional — stdio is the default
      command: npx
      args: ["-y", "@modelcontextprotocol/server-filesystem", "/tmp"]
      env:
        SOME_VAR: "${SOME_VAR}"   # env var substitution
      acl:
        read_file: allow
        write_file: prompt
        "*": deny
```

`npx -y` handles first-run install automatically.

### `streamable-http` — modern remote MCP

HTTP transport using the MCP streamable HTTP spec. Use for hosted MCP services.

```yaml
    - name: my-remote
      transport: streamable-http
      url: https://my-mcp-server.example.com/mcp
      headers:
        Authorization: "Bearer ${MY_TOKEN}"
      acl:
        "*": prompt
```

### `sse` — legacy remote MCP

Server-Sent Events transport. Still common for older remote MCP services.

```yaml
    - name: legacy
      transport: sse
      url: https://legacy.example.com/sse
      headers: {}
      acl:
        "*": prompt
```

### `websocket`

WebSocket transport. Use for real-time bidirectional MCP connections.

```yaml
    - name: ws-server
      transport: websocket
      url: ws://localhost:8080/mcp
      acl:
        "*": prompt
```

# Multi-Agent Composition

Any profile can be called as a tool by another agent. An orchestrator spawns workers, collects results, and synthesises the output.

## The `agents:` block

Declare named sub-agents with typed I/O contracts in the profile:

```yaml
agents:
  - name: researcher
    profile: ./researcher.yaml
    input:
      query: { type: string }
      sources: { type: array }
    output:
      findings: { type: array }

  - name: summariser
    profile: ./summariser.yaml
    input:
      findings: { type: array }
      format: { type: string }
    output:
      report: { type: string }
```

Each `agents:` entry declares:
- `name` — how the orchestrator calls the worker (e.g. `Delegate({ profile: "researcher", ... })`)
- `profile` — path to the worker's profile YAML (relative to the orchestrator's profile)
- `input` / `output` — JSON Schema fragment validated at call time

## `Delegate` tool

Dispatches a single sub-agent synchronously. Returns the worker's final reply.

```json
Delegate({
  "profile": "researcher",
  "task": "Find the top 3 recent papers on transformer efficiency"
})
```

The worker runs its own full agent loop (with its own tools, memory, and MCP servers) and returns when complete.

## `DelegateFanout`

Dispatch N sub-agents in parallel. Pass an array of tasks — all run concurrently, results collected when all complete.

```json
DelegateFanout({
  "profile": "researcher",
  "tasks": [
    "Research transformer efficiency papers",
    "Research quantization techniques",
    "Research mixture-of-experts architectures"
  ]
})
```

Returns an array of results in the same order as the input tasks.

## Depth limit

`max_depth` in the profile prevents infinite recursive delegation. Default: `2`.

- Depth 0 = the orchestrator itself
- Depth 1 = first-level workers
- Depth 2 = workers spawned by workers (if any)

At max depth, `Delegate` calls are rejected with an error.

## Typed I/O contracts

If a worker profile has a `contract:` block, the orchestrator's `Delegate` call is validated against it before the worker runs. Invalid input → error returned immediately, worker not started.

## Example — `profiles/research.yaml`

The `research` profile demonstrates a two-worker orchestration pattern:

```yaml
name: research-orchestrator
model:
  base_url: https://api.anthropic.com/v1
  api_key_env: ANTHROPIC_API_KEY
  id: claude-opus-4-8

system_prompt: prompts/research.md
artifact_dir: .harness/research
max_depth: 2

tools:
  builtin:
    Delegate: allow    # orchestrator needs delegation
    Read: allow
    Write: allow
    Bash: deny         # orchestrator doesn't run shell commands
    ExecuteCode: deny

agents:
  - name: researcher
    profile: ./researcher.yaml
    input:
      query: { type: string }
      sources: { type: array }
    output:
      findings: { type: array }

  - name: summariser
    profile: ./summariser.yaml
    input:
      findings: { type: array }
      format: { type: string }
    output:
      report: { type: string }
```

**Worker profiles:**

`profiles/researcher.yaml` — fetch + brave-search MCP, no Write or Delegate. Focuses on sourcing.

`profiles/summariser.yaml` — Write allowed (artifacts only), no MCP. Focuses on synthesis.

**How the orchestrator uses them:**

1. Receives research query from user
2. `Delegate({ profile: "researcher", task: "Find sources on X" })` → gets `findings`
3. `Delegate({ profile: "summariser", task: "Summarise these findings as a report" })` → gets `report`
4. Returns the report to the user

## Worker profile tips

- Set `improvement.enabled: false` on workers — they run headless and don't benefit from reflection
- Deny tools the worker doesn't need (keeps ACL surface minimal)
- Omit `triggers:` on workers — they're invoked by the orchestrator, not externally

````markdown
# Hooks

Hooks are shell commands that run at agent lifecycle points. They let you integrate the agent loop with external systems — git, logging, alerting, etc.

## Configuration

```yaml
hooks:
  pre_tool: []       # runs before each tool call
  post_tool: []      # runs after each tool call (whether it succeeded or failed)
  on_stop: []        # runs once when the agent loop ends
  timeout_ms: 5000   # max time for any single hook command (default 5000)
```

## Hook points

### `pre_tool`

Runs before each tool call. Receives `TOOL_NAME` env var. If the hook exits non-zero, the tool call is cancelled.

```yaml
hooks:
  pre_tool:
    - "echo '[pre] About to run $TOOL_NAME' >> .harness/audit.log"
```

### `post_tool`

Runs after each tool call, whether it succeeded or failed. Receives both `TOOL_NAME` and `TOOL_OK` (`true` or `false`).

```yaml
hooks:
  post_tool:
    - "echo '[post] $TOOL_NAME ok=$TOOL_OK' >> .harness/audit.log"
```

### `on_stop`

Runs once when the agent loop terminates (user disconnect, error, or natural end). No tool env vars injected.

```yaml
hooks:
  on_stop:
    - "git add .harness/writer/drafts 2>/dev/null || true"
    - "echo 'Session ended' | slack-notify '#ops' 2>/dev/null || true"
```

## Environment variables

| Variable | Available in | Value |
|----------|-------------|-------|
| `TOOL_NAME` | `pre_tool`, `post_tool` | Name of the tool being called (e.g. `Bash`, `Write`) |
| `TOOL_OK` | `post_tool` only | `true` if the tool succeeded, `false` if it threw |

All other environment variables from the server process are also available (`ANTHROPIC_API_KEY`, `PATH`, etc.).

## Timeout

Each hook command runs with a timeout of `hooks.timeout_ms` (default 5000 ms). If a hook times out, it's treated as a failure. For `pre_tool`, a timeout cancels the tool call.

## Failure behaviour

| Hook | Exit non-zero | Timeout |
|------|--------------|---------|
| `pre_tool` | Cancels the tool call | Cancels the tool call |
| `post_tool` | Logged as warning, loop continues | Logged as warning |
| `on_stop` | Logged as warning | Logged as warning |

## Example — `profiles/writer.yaml`

The writer profile uses `on_stop` to stage drafts so nothing is lost if the session ends unexpectedly:

```yaml
hooks:
  on_stop:
    - "git add .harness/writer/drafts 2>/dev/null || true"
```

The `|| true` ensures the hook always exits 0 (even if no drafts exist), preventing a spurious hook-failure warning.

## Tips

- Keep hook commands short and fast — they run on every tool call for `pre_tool`/`post_tool`
- Always use `|| true` for non-critical hooks to avoid spurious failures
- Use `>>` (append) not `>` (overwrite) for log files to avoid losing history
- Hooks run in the server process's working directory, not `profile.working_dir`

# Self-Improvement

After each session, the harness runs a reflection pass to extract learnings and — every N sessions — mine new skills from recurring patterns.

## Configuration

```yaml
improvement:
  enabled: true                      # set false to disable entirely
  model_id: claude-haiku-4-5-20251001  # optional — cheaper model for reflection

## Reflection loop

At the end of every session (on disconnect or `/cancel`):

1. The agent transcript (last session only, trimmed to 8000 chars) is sent to the reflection model
2. The model identifies 0–3 things worth remembering for future sessions
3. Each finding is written to `user` scope memory with a short key

```
# Example: agent learned the user prefers pytest over unittest
MemoryWrite({
  scope: "user",
  key: "test-framework-preference",
  content: "User prefers pytest. Do not suggest unittest."
})
```

These memories are injected into the system prompt for all future sessions with the same profile + user combination.

Every `mine_skills_every_n_sessions` sessions, the reflection model also reviews recent transcripts for recurring patterns. If a pattern appears worth extracting, a proposed skill is written to `<artifact_dir>/learnings/<date>.md` for human review.

## Event schema

```ts
interface TelemetryEvent {
  ts: string          // ISO 8601 timestamp
  session: string     // session ID
  profile: string     // profile name
  kind: 'tool' | 'skill' | 'mcp' | 'llm'
  name?: string       // tool name, skill name, or model ID
  server?: string     // MCP server name (kind=mcp only)
  model?: string      // model ID (kind=llm only)
  duration_ms?: number
  ok?: boolean        // true = success, false = error
  tokens_in?: number  // (kind=llm only)
  tokens_out?: number // (kind=llm only)
  cost_usd?: number   // (kind=llm only)
  trigger?: string    // 'model' for skill loads
}
```

## File location

```
~/.harness/telemetry.jsonl

SESSION=$(tail -1 ~/.harness/telemetry.jsonl | jq -r .session)

## CLI client (readline)

The readline CLI connects to a running server over WebSocket:

```bash
pnpm dev:cli
```

Uses `HARNESS_PORT` (default 7337) and `HARNESS_USER` (default system username).

**In-session commands:**

| Command | Description |
|---------|-------------|
| `/exit` | Disconnect |
| `/cancel` | Cancel the current agent run |
| `/resume <session-id>` | Resume a past session |

## REST API

The server exposes REST endpoints on the same port as the WebSocket server.

**One-shot run:**
```bash
curl -X POST http://localhost:7337/run \
  -H 'Content-Type: application/json' \
  -d '{"input": "Hello", "profile": "coding", "user": "alice"}'
```

**SSE streaming:**
```bash
curl -N http://localhost:7337/stream \
  -H 'Content-Type: application/json' \
  -d '{"input": "Hello"}'
```

**Health check:**
```bash
curl http://localhost:7337/health
```

**Run management:**
```bash
curl http://localhost:7337/runs           # list runs
curl http://localhost:7337/runs/abc123    # get run
curl -X DELETE http://localhost:7337/runs/abc123  # cancel
```

If `HARNESS_API_KEY` is set, include it as a bearer token:
```bash
curl -H 'Authorization: Bearer your-key' http://localhost:7337/run ...
```
