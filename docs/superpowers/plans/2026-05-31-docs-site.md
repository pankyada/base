```markdown
# What is Harness?

Harness is a **generic agent harness** — a thin WebSocket-based runtime that wires a language model to tools, skills, memory, MCP servers, and hooks. Everything is configured through a single YAML profile file.

## What it is not

Harness is not a framework with opinions about your agent's logic. It doesn't dictate prompts, chain structure, or output format. It provides the runtime plumbing — tool execution, ACL enforcement, streaming, session persistence, memory — and gets out of the way.

## Core loop

```
Profile YAML
  ↓ loadProfile()
Server  (ws://localhost:7337)
  ↓ per-connection
  Session  ←→  FsMemoryProvider
  ↓ on user message
  AgentLoop  →  LLM API (streaming)
                  ↓ tool calls
                  ACL check → runHooks(pre_tool) → execute() → runHooks(post_tool)
  ↓ session end
  DefaultImprover.reflect() → memory write + proposed skills
```

## Key concepts

| Concept | What it is |
|---------|-----------|
| **Profile** | YAML file that configures a complete agent: model, tools, memory, hooks |
| **Session** | One conversation between a user and an agent; persisted to `~/.harness/sessions/` |
| **Tool** | A function the agent can call. Built-in, MCP-sourced, or custom JS/TS |
| **Skill** | A Markdown file with frontmatter the agent can read via the `Skill` tool |
| **Memory** | Persistent key-value store scoped to session, profile, or user |
| **Hook** | Shell command that runs before/after tool calls or on session end |
| **Mode** | Trust preset (`developer` / `analyst` / `assistant` / `production`) that sets default ACLs |

## Prerequisites

- Node.js 20+
- pnpm (`npm install -g pnpm`)

```bash
git clone https://github.com/pankyada/base.git
cd base
pnpm install
```

## 2. Configure

```bash
cp .env.example .env
```

OPENAI_API_KEY=sk-...

## 3. Run

```bash
pnpm tui
```

Type a message and press **Enter**. The agent will respond using the `coding` profile by default.

:::tip Profiles
The default profile is `profiles/coding.yaml`. To use a different profile, set `HARNESS_PROFILE` in your `.env` or pass `--profile profiles/data.yaml` to `pnpm tui`.

```
pnpm tui
  └── harness-server (ws://localhost:7337)  ← spawned automatically
  └── Ink TUI                                ← connects to server over WS
```

Quit the TUI with **Ctrl+C**. The server it spawned shuts down cleanly.

# Concepts

## Profile

A YAML file that defines a complete agent. The profile specifies the LLM endpoint, tool permissions, memory config, hooks, and more. See [Profiles](/configuration/profiles) for the full reference.

Profiles live in `profiles/` (project-local) or `~/.harness/profiles/` (user-global). The server loads one profile at startup.

## Session

One conversation between a user and an agent. Sessions are identified by a UUID and persisted to `~/.harness/sessions/<date>_<id>.json`. Each WS connection gets its own session.

## Agent loop

On each user message, the agent loop:

1. Builds the message list (system prompt + history + new message)
2. Calls the LLM API with streaming
3. Receives tool calls; for each: checks ACL, runs pre-tool hooks, executes the tool, runs post-tool hooks
4. Streams the final text response back to the client

## Tool

A function the agent can call. Three sources:

| Source | How to add |
|--------|-----------|
| Built-in | Always available; controlled by `tools.builtin` ACL in profile |
| MCP server | Add to `tools.mcp_servers` in profile |
| Custom | Drop a `.ts` or `.js` file in `.agents/tools/` |

## ACL

Every tool call is checked against the profile's ACL before execution:

| Value | Behaviour |
|-------|-----------|
| `allow` | Execute immediately |
| `prompt` | Pause and ask the user to approve or deny |
| `deny` | Reject the call; agent sees an error |

## Skill

A Markdown file with gray-matter frontmatter (`name`, `description`) that the agent reads via the `Skill` tool. Skills live in `.agents/skills/<name>/SKILL.md`. See [Skills](/tools/skills).

## Memory

Persistent storage the agent can read and write. Three scopes:

| Scope | Where stored | Who can read |
|-------|-------------|-------------|
| `session` | In-memory; lost on disconnect | This session only |
| `profile` | `<artifact_dir>/memory/*.md` | All sessions on this profile |
| `user` | `~/.harness/users/<user>/memory/*.md` | All sessions for this user |

## Hook

A shell command that runs at a lifecycle event. See [Hooks](/configuration/hooks).

## Mode

A named trust preset applied at profile load time. See [Instance Modes](/configuration/instance-modes).
```

# Profiles

A profile is a YAML file that fully describes an agent: which LLM to use, which tools are allowed, where memory lives, and how the session behaves.

## Annotated example

```yaml
# profiles/coding.yaml

name: coding                       # display name; shown in TUI header

model:
  base_url: https://api.openai.com/v1  # any OpenAI-compatible endpoint
  api_key_env: OPENAI_API_KEY          # env var name (not the key itself)
  id: gpt-4o                           # primary model
  fallback_id: gpt-4o-mini             # used if primary rate-limits

system_prompt: ./prompts/coding.md     # path to system prompt file
working_dir: $CWD                      # $CWD expands to process.cwd(); ~ expands to homedir
artifact_dir: .harness/coding          # memory + session artifacts stored here

tools:
  builtin:
    Read: allow      # allow / prompt / deny
    Write: allow
    Edit: allow
    Bash: prompt     # agent must ask user before running shell commands
    Grep: allow
    Glob: allow
    Skill: allow
    MemoryRead: allow
    MemoryWrite: allow
    MemoryList: allow
    MemoryDelete: allow
    Stats: allow
    Delegate: prompt
    ExecuteCode: allow
  mcp_servers:
    - name: filesystem
      transport: stdio
      command: npx
      args: ["-y", "@modelcontextprotocol/server-filesystem", "/tmp"]
      acl:
        "*": prompt
        read_file: allow

hooks:
  pre_tool: []          # shell commands to run before each tool call
  post_tool: []         # shell commands to run after each tool call
  on_stop: []           # shell commands to run when the session ends
  timeout_ms: 5000      # max time per hook (default 5000ms)

improvement:
  enabled: true
  mine_skills_every_n_sessions: 10   # extract reusable skills from session history every N sessions

mode: developer    # optional: developer | analyst | assistant | production

executor:          # optional: enables the ExecuteCode tool
  default: docker
  docker_image: python:3.12-slim
  timeout_ms: 30000
```

### `model`

| Field | Required | Description |
|-------|----------|-------------|
| `base_url` | ✓ | OpenAI-compatible API base URL |
| `api_key_env` | ✓ | Name of the env var holding the API key |
| `id` | ✓ | Model identifier (e.g. `gpt-4o`, `claude-opus-4-8`) |
| `fallback_id` | | Fallback model on rate limit or error |

### `tools.builtin`

Each key is a tool name; value is `allow`, `prompt`, or `deny`. Omitted tools fall back to the `tools.custom` default (default: `prompt`). See [Built-in Tools](/tools/builtin-tools) for the full list.

### `tools.mcp_servers`

Array of MCP server configs. See [MCP Servers](/tools/mcp-servers).

### `hooks`

See [Hooks](/configuration/hooks).

### `improvement`

| Field | Default | Description |
|-------|---------|-------------|
| `enabled` | `true` | Whether the post-session reflection loop runs |
| `mine_skills_every_n_sessions` | `10` | Extract skills every N sessions |

### `mode`

Optional trust preset. When set, its ACL defaults merge into `tools.builtin` (mode wins on conflict). See [Instance Modes](/configuration/instance-modes).

### `executor`

Required to enable the `ExecuteCode` tool. See [Code Execution](/tools/code-execution).

### `context_window`

| Field | Default | Description |
|-------|---------|-------------|
| `max_tokens` | `100000` | Token budget before summarisation |

### `max_depth`

Maximum nested agent delegation depth (default: `2`). See [Multi-agent Composition](/advanced/multi-agent).

Named sub-agent registry for orchestrator profiles. See [Multi-agent Composition](/advanced/multi-agent).

### `contract`

Optional input/output JSON Schema contracts for type-safe programmatic use. See [REST API](/clients/rest-api).

### `triggers`

Cron and webhook triggers. See [Triggers](/advanced/triggers).

### `interop`

A2A and ACP protocol flags. See [A2A / ACP Interop](/advanced/interop).

## Path resolution

| Token | Expands to |
|-------|-----------|
| `$CWD` | `process.cwd()` at server startup |

# Instance Modes

The `mode:` field on a profile applies a named trust preset that sets default tool ACLs and validates the configuration at startup.

## Modes

| Mode | Analogy | Shell access | Code execution | Multi-tenant safe |
|------|---------|-------------|---------------|-------------------|
| `developer` | Claude Code | ✓ (allow) | ✓ (allow) | ✗ — single-tenant only |
| `analyst` | Notebook AI | ✗ (deny) | ✓ (allow) | ✓ |
| `assistant` | ChatGPT | ✗ (deny) | ✗ (deny) | ✓ |
| `production` | Customer-facing agent | ✗ (deny) | ✗ (deny) | ✓ |

## Usage

```yaml
mode: analyst
```

Mode defaults merge into `tools.builtin` at profile load time. Explicit `tools.builtin` values in your YAML override the mode default for that tool.

## Default ACLs by mode

### `developer`

All tools: `allow`. Intended for local single-developer use.

```
Bash, Read, Write, Edit, Grep, Glob, Skill, Stats, Delegate,
AskUser, MemoryRead, MemoryWrite, MemoryList, MemoryDelete,
TodoWrite, TodoRead, ExecuteCode  →  allow
```

:::warning
`developer` mode is not safe for multi-tenant deployments. All destructive tools are unrestricted.
:::

### `analyst`

No shell or file writes; sandboxed code execution allowed.

```
Bash, Write, Edit, Delegate  →  deny
Read, ExecuteCode, AskUser, MemoryRead, MemoryWrite,
MemoryList, MemoryDelete, TodoWrite, TodoRead  →  allow
```

### `assistant`

Read-only filesystem access; no code execution.

```
Bash, Write, Edit, Delegate, ExecuteCode  →  deny
Read, AskUser, MemoryRead, MemoryWrite,
MemoryList, MemoryDelete, TodoWrite, TodoRead  →  allow
```

### `production`

Explicit allowlist only. Any built-in tool not covered by the mode defaults is forced to `prompt`, requiring user approval.

```
Bash, Write, Edit, Delegate, ExecuteCode  →  deny
Read, AskUser, MemoryRead, MemoryWrite,
MemoryList, MemoryDelete, TodoWrite, TodoRead  →  allow
All other tools  →  prompt
```

## Startup validation

`validateMode()` runs at server startup and emits hard errors or warnings:

| Condition | Severity |
|-----------|---------|
| `mode: developer` + `triggers.cron` or `triggers.webhook` | **Hard error** — autonomous developer agents are not allowed |
| `mode: developer` | Warning — not safe for multi-tenant |
| `mode: analyst` + no `executor:` block | Warning — `ExecuteCode` will return "not enabled" |
| `mode: production` + no `contract:` block | Warning — consider adding I/O contracts |
```

# Hooks

Hooks are shell commands that run at lifecycle events. They run outside the agent loop — the agent does not see their output.

## Configuration

```yaml
hooks:
  pre_tool:
    - "echo '[hook] about to run $TOOL_NAME' >> /tmp/harness.log"
  post_tool:
    - "echo '[hook] $TOOL_NAME finished ok=$TOOL_OK' >> /tmp/harness.log"
  on_stop:
    - "./scripts/cleanup.sh"
  timeout_ms: 5000   # each hook command gets this budget; default 5000ms
```

## Lifecycle events

| Event | When it runs |
|-------|-------------|
| `pre_tool` | Before each tool call (after ACL approval) |
| `post_tool` | After each tool call completes |
| `on_stop` | When the session ends (user disconnects or agent finishes) |

## Environment variables

All hooks receive these environment variables:

| Variable | Available in | Value |
|----------|-------------|-------|
| `TOOL_NAME` | `pre_tool`, `post_tool` | Name of the tool (e.g. `Bash`, `Write`) |
| `TOOL_OK` | `post_tool` | `true` if tool succeeded, `false` if it threw |
| `SESSION_ID` | `on_stop` | The session UUID |
| `PROFILE` | `on_stop` | Profile name |

## Multiple commands

Each event accepts an array. Commands run sequentially; if one exceeds `timeout_ms` it is killed and the next runs.

```yaml
hooks:
  pre_tool:
    - "logger -t harness '[pre] $TOOL_NAME'"
    - "./scripts/pre-tool-check.sh"
```

## Use cases

- Audit logging — record every tool call to a file
- Rate limiting — reject tools that run too frequently (exit non-zero to fail the hook)
- Notifications — Slack/webhook on session end
- Cleanup — delete temp files after `Write` calls

:::warning
Hooks run in the server process's shell. Don't use `pre_tool` hooks for security enforcement — ACL is the right mechanism for that.
:::
```

# Built-in Tools

Every harness instance ships with these tools. Enable or restrict them via `tools.builtin` in your profile.

## Tool reference

| Tool | Description | Default ACL |
|------|-------------|-------------|
| `Read` | Read a file with line numbers | `allow` |
| `Write` | Write or overwrite a file | `allow` |
| `Edit` | Exact string replacement in a file | `allow` |
| `Bash` | Execute a shell command (timeout 120s) | `prompt` |
| `Grep` | Regex search across files | `allow` |
| `Glob` | Find files matching a glob pattern | `allow` |
| `Skill` | Load a skill's `SKILL.md` by name | `allow` |
| `MemoryRead` | Read a memory entry by key | `allow` |
| `MemoryWrite` | Write a memory entry | `allow` |
| `MemoryList` | List all memory entries in a scope | `allow` |
| `MemoryDelete` | Delete a memory entry | `allow` |
| `MemoryLinked` | Graph traversal across linked memory entries | `prompt` |
| `Stats` | Report token usage and session cost | `allow` |
| `Delegate` | Run a sub-agent and return its output | `prompt` |
| `DelegateFanout` | Run N sub-agents in parallel | `prompt` |
| `AskUser` | Pause and ask the user a question | `prompt` |
| `TodoWrite` | Write the agent's todo list | `prompt` |
| `TodoRead` | Read the agent's current todo list | `prompt` |
| `ExecuteCode` | Run code in a sandbox (requires `executor:` block) | `allow` |

## Tool details

### `Read`

```
Read(file_path, offset?, limit?)
```

Returns file content with line numbers (`cat -n` format). `offset` and `limit` are 1-indexed line numbers.

### `Write`

```
Write(file_path, content)
```

Writes `content` to `file_path`, creating parent directories if needed. Overwrites existing files.

### `Edit`

```
Edit(file_path, old_string, new_string, replace_all?)
```

Finds `old_string` in the file and replaces it with `new_string`. Fails if `old_string` is not unique (use `replace_all: true` to replace every occurrence).

### `Bash`

```
Bash(command, timeout?)
```

Runs `command` in a shell subprocess. `timeout` defaults to 120,000ms (2 minutes). stdout and stderr are combined in the return value.

### `Grep`

```
Grep(pattern, path, flags?)
```

The harness connects to [Model Context Protocol](https://modelcontextprotocol.io) servers and exposes their tools to the agent. Four transports are supported.

## Configuration

```yaml
tools:
  mcp_servers:
    - name: filesystem

### `stdio` (default)

Spawns a local subprocess. Best for local tools.

```yaml
- name: filesystem
  transport: stdio              # can be omitted
  command: npx

  env:
    MY_VAR: value
  acl:
    "*": prompt
```

### `streamable-http`

Connects to a remote MCP server over HTTP. Modern standard.

```yaml
- name: my-remote
  transport: streamable-http
  url: https://my-mcp-server.com/mcp
  headers:
    Authorization: "Bearer ${MY_TOKEN}"
  acl:
    "*": prompt
```

### `sse`

Connects to a remote MCP server over Server-Sent Events. Legacy but still common.

```yaml
- name: legacy
  transport: sse
  url: https://legacy.example.com/sse
  headers: {}
  acl:
    "*": prompt
```

### `websocket`

Connects to a remote MCP server over WebSocket.

```yaml
- name: ws-server
  transport: websocket
  url: ws://localhost:8080/mcp
  acl:
    "*": prompt

  write_file: deny     # deny a specific tool

Each WebSocket connection gets its own set of MCP client connections. MCP servers are not shared between sessions.

# Code Execution

The `ExecuteCode` built-in tool runs sandboxed code. It requires an `executor:` block in the profile.

## Quick setup

```yaml
executor:
  default: docker
  docker_image: python:3.12-slim
  timeout_ms: 30000
```

## How it works

```
ExecuteCode(code, language, data?)
  ↓
executor.default = 'wasm'  AND  client signals wasm_supported: true
  → code_execute WS message → Pyodide in browser → code_result back

executor.default = 'docker'  OR  client doesn't support WASM
  → Docker subprocess: --rm --network none --memory 512m --cpus 1
```

## Executor config

```yaml
executor:
  default: docker         # 'wasm' or 'docker'
  fallback: docker        # always 'docker' (WASM falls back to Docker for non-Python)
  docker_image: python:3.12-slim
  timeout_ms: 30000
  allowed_packages: []    # pre-loaded into Pyodide on client boot (WASM only)
```

## WASM executor

When `default: wasm` and the client signals `wasm_supported: true` in its `hello` message, the server sends a `code_execute` WebSocket message to the browser. The browser runs the code in [Pyodide](https://pyodide.org) (Python in WASM) and returns the result.

- Only supports `language: python`
- Non-Python falls through to Docker automatically
- No server-side attack surface for analyst workloads

## Docker executor

Spawns a Docker container with:
- `--rm` — auto-remove on exit
- `--network none` — no network access
- `--memory 512m` — memory cap
- `--cpus 1` — CPU cap
- `--user 1000:1000` — non-root

The working directory is mounted read-only at `/work`. Output files written to `/out` are returned base64-encoded in the result.

## Passing data to code

```typescript
// Agent call:
ExecuteCode(
  code: "import json; d = json.load(open('/data/data.json')); print(d['x'] * 2)",
  language: "python",
  data: { x: 21 }
)
// data is written to /data/data.json inside the sandbox
```

## Result format

```
exit_code: 0
duration_ms: 312
stdout: 42
stderr: (empty)
files: {}   // files written to /out, keyed by filename, base64-encoded
```

## Disabling code execution

```yaml
tools:
  builtin:
    ExecuteCode: deny
```

# Memory Overview

Memory is a persistent key-value store the agent reads and writes during a session. Entries are Markdown files with gray-matter frontmatter.

## Scopes

| Scope | Where stored | Lifetime |
|-------|-------------|---------|
| `session` | In-memory on the `Session` object | Lost on disconnect |
| `profile` | `<artifact_dir>/memory/*.md` | Persists across sessions on this profile |
| `user` | `~/.harness/users/<user>/memory/*.md` | Persists across all sessions for this user |

`MemoryWrite` defaults to `user` scope. Pass `scope: "profile"` or `scope: "session"` to override.

## Tools

```
MemoryWrite(key, content, scope?)   // write or update an entry
MemoryRead(key, scope?)             // read one entry
MemoryList(scope?)                  // list all entry keys in a scope
MemoryDelete(key, scope?)           // delete an entry
MemoryLinked(key, scope?, relation?, depth?)  // graph traversal (graph provider only)
```

## Providers

Two providers are available, configured per-profile:

```yaml
memory:
  provider: fs      # default: 'fs' or 'graph'
```

| Provider | Description |
|----------|-------------|
| `fs` | Plain Markdown files. Simple, human-readable, git-friendly. |
| `graph` | Adds typed relation links between entries. Enables `MemoryLinked` traversal. |

## System prompt injection

At session start, profile-scoped and user-scoped memory entries are injected into the system prompt so the agent has context from previous sessions.

## Two-tier memory

Shared knowledge (facts about the project, recurring patterns) lives in `profile` scope. Private knowledge (user preferences, personal context) lives in `user` scope. The combined view is presented to the agent.
```

```markdown
# Graph Provider

An enhanced memory provider that stores entries as nodes in a graph with typed, bidirectional relation links.

## Configuration

```yaml
memory:
  provider: graph
```

## Graph structure

Each memory entry is a node. Relations are typed edges:

```
project-stack ──[uses]──► typescript
project-stack ──[uses]──► vitepress
auth-decisions ──[supersedes]──► old-auth-approach
```

## Storage

The graph is persisted to `<artifact_dir>/memory/graph.json`.

## `MemoryLinked` traversal

```
MemoryLinked(key, scope?, relation?, depth?)
```

Starting from `key`, follows links up to `depth` hops (default 1). Filter by `relation` type to narrow the traversal.

```json
// Example: find everything "project-stack" uses
MemoryLinked("project-stack", "profile", "uses", 1)

// Returns:
[
  { "key": "typescript", "relation": "uses", "content": "..." },
  { "key": "vitepress",  "relation": "uses", "content": "..." }
]
```

## When to use graph vs FS

Use `graph` when:
- The agent needs to navigate relationships between memory entries
- You want typed traversal (e.g. "find all decisions that supersede X")
- Memory entries reference each other frequently

Use `fs` (default) when:
- Memory entries are independent
- You want simple human-readable files
- You're starting out
```

# Multi-agent Composition

Any profile can be exposed as a sub-agent callable by an orchestrator.

## Named sub-agent registry

In the orchestrator's profile, list sub-agents:

```yaml
agents:
  - name: researcher
    profile: ./profiles/researcher.yaml
    input:
      query: { type: string }
    output:
      summary: { type: string }
  - name: writer
    profile: ./profiles/writer.yaml
    input:
      outline: { type: string }
    output:
      draft: { type: string }
```

## `Delegate` — sequential sub-agent call

```
Delegate(agent_name, input)
```

Runs one sub-agent and returns its output. The orchestrator's agent loop is paused until the sub-agent finishes.

```json
// Example
Delegate("researcher", { "query": "What is VitePress?" })
// Returns: { "summary": "VitePress is a static site generator..." }
```

## `DelegateFanout` — parallel fan-out

```
DelegateFanout(agent_name, inputs[])
```

Runs the named sub-agent N times in parallel, one per element of `inputs`. Returns an array of outputs in the same order.

```json
// Example: research 3 topics in parallel
DelegateFanout("researcher", [
  { "query": "VitePress" },
  { "query": "Vitest" },
  { "query": "Vite" }
])
// Returns: [{ "summary": "..." }, { "summary": "..." }, { "summary": "..." }]
```

The `input` and `output` blocks in `agents:` are JSON Schema fragments. The orchestrator validates sub-agent inputs and outputs against these schemas.

## Depth limit

`max_depth` in the profile limits how deeply agents can nest (default: `2`). A depth-3 call from a depth-2 orchestrator fails with a depth error.

```yaml
max_depth: 3
```

  -d '{ "input": "What files are in this directory?", "user": "alice" }'
```

**Request body:**

| Field | Required | Description |
|-------|----------|-------------|
| `input` | ✓ | User message (string or JSON object) |
| `user` | | User ID for session/memory scoping |
| `profile` | | Profile name override |

**Response:**

```json
{
  "output": "The directory contains...",
  "usage": { "input_tokens": 450, "output_tokens": 120 },
  "session_id": "abc123"
}
```

:::tip
`prompt`-ACL tools are auto-denied in headless REST runs — no interactive approver is available.
:::

### `POST /stream`

Streaming agent run via Server-Sent Events.

```bash
curl -X POST http://localhost:7337/stream \
  -H "Content-Type: application/json" \
  -H "Accept: text/event-stream" \
  -d '{ "input": "Summarise this repo", "user": "alice" }'
```

**SSE event types:**

| Event | Payload |
|-------|---------|
| `token` | `{ "text": "..." }` — partial response token |
| `tool_start` | `{ "name": "...", "input": {...} }` |
| `tool_end` | `{ "name": "...", "ok": true, "output": "..." }` |
| `stats` | `{ "input_tokens": N, "output_tokens": N, "cost_usd": N }` |
| `result` | `{ "output": "..." }` — final assembled response |
| `error` | `{ "message": "..." }` |

## Input/output contracts

If the profile defines a `contract:` block, `/run` and `/stream` validate the `input` field against `contract.input` and return a 422 error on violation:

```yaml
contract:
  input:
    type: object
    properties:
      query: { type: string }
    required: [query]
```

```bash
# This returns 422 because "query" is missing
curl -X POST http://localhost:7337/run \
  -d '{ "input": { "wrong_field": "value" } }'
